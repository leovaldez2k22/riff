# Riff playback startup path and existing evidence

## What does the current implementation do?

### Takeaway
Riff already implements important startup techniques: process-owned resolver, cached prepared player text, warm-up, 32-entry expiring URL cache with single-flight sharing, next-song resolution after 3 seconds, reusable HTTP connection pool, 256 MiB byte cache and verified offline downloads. The largest evidenced opportunity is cold stream extraction and its competition with speculative warm-up, not the UI queue animation. Two fundamentally different resume branches must remain separate.

### Cited findings
All paths below are relative to C:/Volume D/Riff and were read on 2 November 2026; these are current local implementation sources, not assumed upstream behavior.

- Media3 is pinned to 1.11.1, innertubex to 0.7.2. Source: [versions](</C:/Volume D/Riff/gradle/libs.versions.toml:7>).
- Mini-player Play enters gateway toggle, start and playFromUser. An IDLE player prepares, ENDED seeks, then play runs. A READY retained player can resume without resolving or invoking the solver. Source: [gateway](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackGateway.kt:249>), [playFromUser](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackGateway.kt:511>).
- Restored YouTube queue is rebuilt as catalog items, deliberately unprepared and paused. Existing queue/index/position is preserved; former signed stream URLs are not persisted. Source: [restore](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/QueueCoordinator.kt:158>).
- Fresh normal single-song selection sends an unresolved queue; collection selection sends multiple catalog items. Source preparation resolves on demand via DeferredProviderSource. Source: [source](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackSources.kt:74>), [deferred source](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/DeferredProviderSource.kt:24>).
- Before resolution, source checks offline audio and bundle validity; local file playback bypasses extraction. Invalid downloads are marked damaged and streaming attempted. Source: [download selection](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackSources.kt:85>).
- Selected source has a 30s resolver deadline, live 60s. Resolver itself creates process-owned async flights with a 60s deadline. Source cancellation/30s timeout does not necessarily cancel the shared longer-lived flight. Flights keyed by auth revision, video, live/video/download, quality and stream revision; RAM cache bounded at 32. Source: [source deadline](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackSources.kt:101>), [resolver](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:160>).
- One cancellation-refresh retry waits 150ms before restarting extraction if the async flight is itself still active. Source: [refresh retry](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:169>).
- Cache eligibility requires non-live and >60s expiry margin. Constructed expiry is min(provider expiry, now+20min). This is not an explicit 5min freshness policy. Source: [cache policy](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/MusicCachePolicy.kt:3>), [expiry](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:250>).
- Cold initializer marks warmedAt immediately then launches an untracked 2s-delayed warmup. Foreground warmUp coalesces its own tracked warming job and throttles on a 5min timestamp. This allows the immediate foreground call to be suppressed before delayed cold warmup actually completes. Source: [cold initialization](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:103>), [warmup](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:119>).
- Warmup starts second-player script preload beside visitor settlement/extractor prewarm; it can perform another late preload. Source: [prewarm](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:136>).
- Explicit lookUpNext starts only while current isPlaying, waits 3000ms, checks download, resolves next URL into provider RAM cache; it does not fetch next compressed audio bytes. Media3 following-source preparation is separate and can run sooner; source itself has no selected-first gate. Source: [lookUpNext](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackSources.kt:55>), [delay constant](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackSources.kt:147>).
- Crossfade separately configures ExoPlayer 12s preloading when enabled. Do not claim Riff has no preload. Source: [crossfade](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/Crossfade.kt:273>).
- Token provider serializes with mutex; cached visitor token/runtime invalidated on visitor/cookie change or advertised integrity expiry. Cold stages: watch GET, interpreter GET, JS BotGuard, GenerateIT POST, minter creation, visitor mint then per-video mint. JS evaluate callback lacks local deadline; token polling has 17s budget and first WebView load 10s. Source: [token](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/AndroidStreamTokenProvider.kt:63>), [runtime](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/AndroidTokenRuntime.kt:32>).
- Native cipher is isolated in solver process; 10min idle unbind and disposal release heaps. Existing idle timer is canceled/rescheduled after transaction success rather than at call entry, allowing timer race with in-flight request. Binder transact synchronous; coroutine timeout does not physically abort it. Bind deadline15s; crash retry once includes process-gone wait5s+250ms. Source: [remote client](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/RemoteCipherClient.kt:33>), [transaction](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/RemoteCipherClient.kt:91>), [idle timer](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/RemoteCipherClient.kt:159>).
- SolverGate gives foreground lookups priority over speculative preloads that have not entered library, but cannot preempt existing library mutex holder or order selected lookup over next lookup. Source: [gate](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/SolverGate.kt:3>), [service](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/SolverService.kt:58>).
- Prepared player text is persisted separately; it does not retain a live JS runtime. Pinned-bytecode investigation finds per-call EJS evaluation and shared cipher serialization; use pinned evidence rather than guessing current upstream. Source: [prior forensic report](</C:/Volume D/Riff/artifacts/idle-forensics-20261101/report.md>).
- Shared OkHttp progressive audio pool has 8s connect/read limits; no startup call-wide deadline. Byte-cache source chosen after URL resolution for ordinary HTTPS/SABR audio. Stable key includes account scope, transport, video, itag, MIME, bitrate; format identity is important. Thus cached bytes may still await resolver in a restored catalog queue. Sources: [stream client](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/OkHttpStreamDataSource.kt:128>), [byte cache](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/MusicDiskCache.kt:12>), [source cache selection](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackSources.kt:127>), [cache identity](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/MusicCachePolicy.kt:6>).
- riffLoadControl only changes back buffer; it does not tune startup thresholds. Prior pinned-bytecode analysis establishes 1000ms media duration initially,2000ms rebuffer,50s forward loading. These are media duration, not mandatory wall-clock delay. Source: [load control](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/VolumeBoostProcessor.kt:109>), [forensic dependency evidence](</C:/Volume D/Riff/artifacts/idle-forensics-20261101/report.md>).
- Signed-in ordinary song usually uses direct audio; SABR principally signed-out fallback, so it should not be assumed root of signed-in idle reproduction. Source: [stream hints](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:341>).
- Recovery is bounded:3 attempts,0/1/3s delays+jitter,60s active online episode; layered Media3 loading retries may precede coordinator. Source: [recovery policy](</C:/Volume D/Riff/app/src/main/java/com/musicglass/personal/PlaybackRecovery.kt:75>).

### Inferences
- Strong first candidate: selected startup must outrank warmup, next-source extraction and analysis; avoid speculative work taking the cipher mutex before Play. A gate cannot preempt existing work.
- Next-song URL prefetch plus bounded byte/prepared-source preload can improve skips, but not arbitrary first track selection unless it predicts the user correctly. Handle metered network, changed queue and quality/account invalidation.
- Repeated already-cached tracks may benefit from cache-first playback using validated format metadata, but bypassing resolution safely requires a durable mapping of exact format/cache completeness and scope. Do not blindly play cached bytes by video ID alone.
- Shortening URL TTL can worsen startup by forcing more extraction. Tuning startup buffers cannot remove seconds spent before media bytes/source exist.

### Gaps
- No current root cause proven for every delayed startup. New first-song, warm skip, restored queue, surviving prepared resume, signed-out and download are different paths.

## What does existing phone evidence establish?

### Takeaway
Actual existing evidence is stronger and more current than some summary text: one deliberate cold-restored control took7.160593s, while a surviving prepared player resumed after19min idle in0.561217s despite13.781s overlapping warmup. The cold run concentrates delay before decode, inside resolver/cipher RPC. These are few debug samples and native callback estimates, not acoustic measurements or p95.

### Takeaway
Build on existing diagnostics and candidate bundle, split the candidates, then measure selected changes on the affected branch. Do not apply all speculative policies as a claimed proven solution.

### Inferences
Recommended priority: (1) classify real delayed startup branch; (2) fix solver active-call idle lease independently; (3) selected-first resolution and coalesced completion-based foreground warmup, defer speculative work; (4) if per-song EJS dominates even warm selected-first runs, investigate dependency-level safe retained runtime/compiled functions or solving only selected format, under isolation and memory limits, rather than copying incompatible app code; (5) bounded next-song byte/prepared-source preloading; (6) scoped JS/network guards only if traces need them; (7) tune buffers after network/extraction is out of critical path.

For validation keep account,track,queue,position,quality,network,output route,cache and thermal matched. Use native output plus acoustic/loopback if actual sound complaint differs; compare BitChord only on same track/auth/network/quality/cache conditions. Track extraction count,memory,thermal,bytes,rebuffer and battery alongside latency. Finish required PR lane before calling implementation done; this research made no app changes and ran no verification lane.
