# Native audio, providers, storage and OS integration

## What exists and what can be reused?

### Takeaway
Riff already has a mature Android playback/provider architecture. Desktop must preserve its contracts and account boundaries while replacing Android service, Media3, Binder, WebView-cookie, media-session and file-system adapters. Replacing everything with yt-dlp would discard working application behavior rather than merely remove CORS.

### Cited findings
- The existing owner is MusicPlaybackService with Media3 main/tail ExoPlayers, queue/recovery/persistence/audio-transition coordinators; the challenge solver is isolated in `:solver`. The document is historical 0.10.0/Q19 architecture and current source is authoritative: [architecture](C:/Volume%20D/Riff/docs/quality/architecture.md:12).
- Current provider is InnertubeX 0.7.2 and Ktor 3.5.2, with Media3 1.11.1 and ONNX Runtime Android 1.31.1: [dependencies](C:/Volume%20D/Riff/gradle/libs.versions.toml:7), [provider dependency](C:/Volume%20D/Riff/gradle/libs.versions.toml:36). No Spotify extraction baseline was found.
- `ProviderSessionManager` owns HTTP, session generation, reset, cookies, scope and account identity; it imports Android Context/CookieManager and SharedPreferences. The current wrapper is not directly JVM-desktop compatible: [source](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/ProviderSessionManager.kt:1), [ownership contract](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/ProviderSessionManager.kt:34).
- `ProviderStreamResolver` uses AndroidStreamTokenProvider and RemoteCipherClient; signed stream addresses remain only in bounded RAM, never durable metadata/logs, with account reset invalidation and deduplicated in-flight resolutions: [source](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:45), [RAM rule](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:159). It handles direct, HLS and SABR choices, including known signed-out failures: [transport choices](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/ProviderStreamResolver.kt:338).
- Local metadata already uses Android SQLiteOpenHelper v3 with WAL: [LibraryState](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/LibraryState.kt:27). Streaming audio already has a 256 MiB Media3 SimpleCache: [cache](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/MusicDiskCache.kt:12). Downloads are separate durable OfflineMusicStore files; do not treat caches as offline downloads.
- Existing media processing is not simple play/pause: PcmEqualizer, volume boost/normalization, main/tail mixing, silence watch and PcmEcho. Equalizer and echo are pure math cores inside Android AudioProcessor wrappers: [EQ](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/EqualizerProcessor.kt:26), [echo](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/EchoProcessor.kt:27). Renderer ordering explicitly places supplied stages before the booster: [sink construction](C:/Volume%20D/Riff/app/src/main/java/com/musicglass/personal/VolumeBoostProcessor.kt:89).
- Recent Automix behavior includes six-step handoff, bass/body levels, downbeat swap, vocal overlap prior, sample-placed echo, predictive trim and 64s local/45s stream tails. CPU/model scheduling proposals remain owner-deferred. The seven fixes have unit coverage but incomplete listening/corpus measures: [handover](C:/Volume%20D/Riff/docs/handover-0.20.0.md:180). Keep current behavior; do not silently optimize away analysis or claim proven beat matching.

### Inferences / proposed architecture
Use a persistent Kotlin/JVM desktop host owning session/provider, library/queue coordinator, SQL database, caches, OS adapters and tray. Compose windows are disposable views. A native audio worker owns decoding, realtime mixing/DSP, device I/O and the sample clock. Kotlin communicates over bounded framed private stdio or a per-user named pipe; no public HTTP control server. The JVM remains alive in tray, which is acceptable because fidelity/reliability outrank an arbitrary 100 MiB cap. UI crash survival is not promised by this topology. Close-to-tray must not cancel application-scoped coroutines, provider renewal or the worker. Explicit Quit ends both processes.

Share model/planner rules and golden fixtures first; decide which pure Kotlin files move only after Android dependency scan. Provider reuse requires proving the pinned InnertubeX dependency publishes a usable desktop/JVM variant; platform wrappers, token provider and solver must be rewritten. Do not assume Android Media3 ExoPlayer runs as a desktop engine. The plan's one-`:app` rule is current Android architecture; adding desktop/shared Gradle modules is a proposed ADR requiring explicit acceptance, not an accidental cleanup.

### Gaps
Desktop Google session acquisition and token/challenge solving must be proven using test credentials before M3 can promise signed-in parity. The Android CookieManager mechanism cannot simply be copied. A normal browser OAuth flow must not be advertised without a supported provider auth flow; do not scrape the owner's browser profile or request credentials on the command line. SABR/progressive/HLS streaming, live/podcasts and download repacking require dedicated fixtures.

## Which audio engine and synchronization architecture?

### Takeaway
Native playback is the recommended placement. Select one device callback and one output sample clock for two-deck mixing. Rust CPAL plus pinned FFmpeg decoding and custom DSP is a practical proposed baseline; CPAL plus Symphonia is a smaller alternative only after exact codecs/containers and gapless metadata pass. Rodio and miniaudio are useful layers, not automatic gapless/Automix guarantees.

### Cited findings
- WebAudio has a rendering thread distinct from the control thread; AudioWorklet supports DSP there. It is inaccurate to say every frontend audio frame runs on the UI thread. It still depends on the lifetime of the relevant renderer/audio context: [W3C WebAudio](https://www.w3.org/TR/webaudio-1.0/).
- CPAL provides low-level device/stream callbacks and dedicated high-priority callback execution on modern platforms. It does not supply decoding, gapless scheduling, networking or DSP: [CPAL](https://docs.rs/cpal/latest/cpal/).
- Rodio provides decoded sources, sequential sources and mixing on an audio thread; retaining its handle is necessary for playback. Its abstraction alone is not evidence of sample-perfect playlist transitions: [Rodio](https://docs.rs/rodio/latest/rodio/).
- Symphonia is demux/tag/decoding, with an explicit supported codec/container table. Current table lists Opus with missing quality/feature fields rather than established coverage; pin and test exact release rather than claiming all YouTube formats work: [Symphonia](https://github.com/pdeljanov/Symphonia).
- Miniaudio exposes low/high-level device and mixing APIs and custom decoding backends; its manual warns against stop/start device calls inside callbacks and against assuming shared-library ABI compatibility across versions: [miniaudio](https://miniaud.io/docs/manual/index.html).
- FFmpeg licensing depends on build configuration and optional components; package the exact source/configuration and notices, consistent with Riff GPL-3.0 distribution: [FFmpeg license requirements](https://ffmpeg.org/legal.html).

### Inferences / proposed requirements
Renderer HTML audio is attractive for an existing web UI, but Riff has neither web components nor WebAudio DSP. It adds no source-reuse advantage. A renderer kept alive can play in tray, but disposing it stops its audio ownership. Native playback allows all windows and GPU loops to stop without stopping music. A mature libmpv backend could reduce transport work, but two independent player clocks and advanced custom sample DSP demand a specific prototype; it is not the default while existing Automix must be preserved.

Worker pipeline: transport/decoder workers -> bounded PCM rings per deck -> per-deck EQ/normalization/transition DSP -> one mixer -> output device. Port existing bass/above-bass shelf, echo timing, gain limiting and boost equations with golden PCM tests; do not use generic library crossfade as a replacement. Decode/preload upcoming audio off the realtime callback. Callback has no locks, allocations, file/network I/O, IPC serialization, logging or model inference. Device loss is handled by coordinator state and device reinitialization outside callback. Rebuild/resample at actual selected device rate; support 44.1/48 kHz transition fixtures and non-stereo source mapping. Seeking increments timeline epoch so delayed events cannot rewind the UI.

Gapless means no app-inserted silence between adjacent content samples after encoder delay/end-padding trim; authored silence is retained. It is separate from crossfade. Proposed validation: synthetic continuous-tone split files across MP3/AAC/Opus/FLAC/WAV fixtures, inspect boundary PCM for added/dropped samples and discontinuities; decoded reference comparison with codec tolerance; capture 30-minute device playback under resize/search/art decode/inference stress with zero underruns. Test track end, seek while blending, stop while echo ringing, output unplug/replug, sleep/resume, network loss, corrupt/truncated files. Do not promise sample-perfect output for compressed streams without container-delay metadata or before tests establish it.

Authoritative events include content position, rendered/output frame count, sample rate, playback rate, output latency estimate and monotonic timestamp. UI estimates the current audible content position locally; it never uses wall clock, decodes time from animation duration, or asks native code 120 times/s. Send clock anchors at 5-10Hz and immediately on seek/pause/rate/track/device change. Lyrics timings are fetched/cached once per track and evaluated against the same clock in Compose's frame loop. Proposed sync budget: lyric boundary within 30ms of reference at steady playback and corrected within 100ms after seek, measured with known fixtures.

Visualizer uses a post-mix tap into a lock-free ring; analysis worker makes FFT/rms/peak packets. No PCM through ordinary JSON. 256 uint16 FFT bins *60Hz is 30,720 bytes/s plus headers; 512 f32 bins *60Hz is 122,880 bytes/s plus headers (calculations, not measured bridge throughput). Use latest-only/drop-old semantics and subscription lifetime; never backpressure audio because UI is slow. At 120Hz visual rendering interpolate 60Hz spectrum packets. Drop to zero while no relevant window is visible. Shared memory is unnecessary until profiling finds framed pipes inadequate. Worker telemetry logs overruns and queue depths without content/addresses.

## Provider sidecars, OS services, data and security

### Takeaway
Keep extraction and transport behind a native/JVM boundary, preserve the existing provider abstraction, and add yt-dlp only as an optional replaceable adapter after a compatibility audit. Windows 11 is the initial shipping platform. macOS/Linux integrations are designed interfaces and future work, not claims of delivered support.

### Cited findings
- yt-dlp publishes signed SHA256/SHA512 checksum manifests and supports explicit release/update channels. Modern YouTube extraction can require an external JS runtime, with supported runtimes and Deno default documented; a sidecar bill of materials may include more than yt-dlp/FFmpeg: [yt-dlp](https://github.com/yt-dlp/yt-dlp).
- Windows SMTC can be manually integrated for a custom engine. `ISystemMediaTransportControlsInterop::GetForWindow` requires a top-level HWND belonging to the calling process: [Win32 SMTC interop](https://learn.microsoft.com/en-us/windows/win32/api/systemmediatransportcontrolsinterop/nf-systemmediatransportcontrolsinterop-isystemmediatransportcontrolsinterop-getforwindow). Automatic MediaPlayer integration is a separate path and not applicable to CPAL: [SMTC overview](https://learn.microsoft.com/en-us/windows/apps/develop/media-playback/integrate-with-systemmediatransportcontrols).
- RegisterHotKey registers system-wide shortcuts and can fail; Windows-key combinations are reserved. Treat conflicts as normal settings outcomes: [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey).
- Windows tray is the notification area with Shell notification icon APIs: [tray API](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area).
- `SetThreadExecutionState` controls system/display sleep requirements; use a playback-scoped system requirement and clear it on pause/end. Audio-only playback should permit display sleep; do not use away mode as an ordinary music-player default: [Microsoft power API](https://learn.microsoft.com/en-us/windows/desktop/api/winbase/nf-winbase-setthreadexecutionstate).
- Apple separates now-playing metadata and remote commands: [MPRemoteCommandCenter](https://developer.apple.com/documentation/mediaplayer/remote-command-center-events). Linux MPRIS2 defines standard D-Bus player methods/properties: [MPRIS2](https://specifications.freedesktop.org/mpris/latest/Player_Interface.html).
- Discord's current SDK documents unauthenticated RPC Rich Presence transport. Do not embed a Discord user token or bot token: [Discord release notes](https://discord.com/developers/docs/social-sdk/release_notes.html), [official Rich Presence overview](https://github.com/discord/discord-api-docs/blob/main/developers/rich-presence/overview.mdx).
- SQLite WAL enables concurrent readers with a writer but requires checkpoint management and local-host storage. It is not multiple concurrent writers: [SQLite WAL](https://www.sqlite.org/wal.html). Live backups should use the online backup API: [backup](https://sqlite.org/c3ref/backup_finish.html).
- Windows DPAPI encrypts data normally bound to the user's credentials and computer, appropriate for local provider session secrets, not portable account backup: [CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

### Inferences / proposed design
Provider resolution returns opaque source handles plus expiry, codec/container/range/transport capabilities, not cookie-bearing URLs in UI. Native/JVM HTTP bypasses browser CORS naturally; no `--disable-web-security`. CORS absence does not eliminate expiring tokens, authentication refusals or extraction breakage. Deduplicate lookup per account/track/format, renew with expiry margin, apply bounded exponential retry/jitter and Retry-After; keep a single recovery budget and stale account-generation cancellation. Never rotate accounts/proxies as a rate-limit workaround.

Use in-process transport when native decoder can consume controlled byte streams. Add loopback proxy only where decoder URL/range integration requires it: bind loopback ephemeral port, unguessable per-session bearer, restricted methods/paths, source handles rather than arbitrary fetch URLs, request-size/range limits, redirect+DNS validation and upstream host allowlists, correct Content-Range/206, seek cancellation and bounded buffers. Do not expose it on LAN or accept file://, arbitrary destinations or renderer-supplied headers. Native audio callback cannot fetch from proxy.

If yt-dlp is needed, pin a platform/architecture build, run with argument arrays and fixed flags, no shell interpolation/user arbitrary flags, time/memory/output limits, no cookies in arguments/logs, stdout bounded structured JSON. Disable ambient config/plugin execution. Independently stage authenticated updates into a versioned directory, verify signature/hash against trusted signed manifest, smoke-test extraction, atomically select new version, retain known-good rollback. Do not run uncontrolled self-update on each play, mutate a signed installed bundle, or mix updated binary with unknown JS runtime. Windows app updater and extraction-adapter updates need separate rollback/version manifests. Exact FFmpeg configuration/codec inventory enters SBOM and NOTICE. No sidecar needed solely because web frontends have CORS.

SMTC adapter belongs in the persistent Kotlin host (JNI/JNA/native DLL), not the audio worker borrowing host HWND; retain a suitable hidden top-level host window when visible Compose windows close, and verify interop lifecycle on real Windows 11. SMTC/tray/keyboard all submit the same typed coordinator commands, preventing double toggles. Restore after Explorer restart, define close/minimize/Quit explicitly, make close-to-tray discoverable, and guarantee explicit Quit removes icon/SMTC/power requests. Register media controls without stealing normal Space/Ctrl+K outside the app. Discord is optional/off until user enables listening disclosure; sends only approved display metadata and clears presence on stop/quit, reconnecting without blocking audio. Native tray menus may use OS conventions; custom in-app menus retain Riff design.

Retain account-scoped SQLite schemas, queue entry identity, history/privacy and local-vs-provider distinctions. Desktop SQLite driver changes bindings, not data semantics; migrations are transactional and tested with old fixtures. One writer queue, small transactions, indexed scope+sort/search keys and FTS for large libraries; readers on IO threads. Short cursor lifetimes and scheduled checkpoints keep WAL bounded. Metadata does not include signed stream addresses. Session cookies encrypted with DPAPI and restrictive user ACLs; no imported owner secrets in tests.

Audio cache key = account scope + provider media id + representation/format/revision, not expiring signed URL. Track verified byte ranges/completeness/hash and distinguish incomplete cache from durable validated downloads; eviction avoids playing and downloading files and uses per-cache quotas. Corrupt/truncated downloads become damaged and do not retry indefinitely (existing 0.20.0 fix must survive). Scope erasure removes cache/index entries as promised by privacy policy.

Cover art pipeline: deterministic source+revision+size variant key, encoded disk LRU, bounded decoded-memory LRU, visible-item prefetch and single-flight request. Precompute palette/backdrop from the same decoded image and associate all outputs with artwork generation; late old-cover results cannot recolor new track. Reserve image geometry, retain current image until new image+palette are ready, then run the existing artwork crossfade. Cached placeholder uses saved palette with identical bounds, preventing shift/flicker. Do not decode dozens of 1024px covers for a library list. Performance budgets remain proposed until measured on packaged Windows builds; neither tray RAM nor stream URL success is guaranteed from library choice alone.

### Verification and unresolved decisions
Prove desktop session/solver and signed-out provider matrix early in M3; no writes to owner's YouTube account during research/tests. Require owner approval before account mutation or publication. Measure worker+JVM+GPU total memory, cold start, first local/online audio, decode/seek, gapless/DSP reference parity, actual tray CPU and reconnect behavior. Future mac/Linux OS adapters have contract tests only until hardware validation. Keep owner-deferred Automix CPU/thermal decisions unchanged and document remaining 50-song/listening gates. No implementation-stage PASS or PR-lane completion is claimed by this research.

Implementation clarification: proposed FFmpeg decoding means pinned native libavformat/libavcodec/libswresample linked into the worker, with a narrow tested FFI layer; it does not mean launching an ffmpeg CLI per song and piping unbounded PCM. Decoder workers trim encoder delay/end padding where metadata is available and normalize both decks to one negotiated mix rate before the single device callback. Gapless behavior across differing source sample rates is explicitly tested. A pure Rust CPAL+Symphonia implementation remains a decoder-spike alternative; select only after the pinned versions pass AAC/Opus/container/seek/padding coverage. Transport credentials and any expiring URLs crossing host-to-worker remain ephemeral and redacted from diagnostics. Private inherited pipes are preferred; Windows named-pipe alternatives need a per-user security descriptor and authenticated instance handshake. Artifacts must include the exact FFmpeg source/build configuration and license notices required for the chosen enabled components; this is a distribution deliverable, not a claim that every FFmpeg build has the same license.
